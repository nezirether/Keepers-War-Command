# Keepers War Command guild synchronization audit

**Baseline** 086f382eb3e39a269ec83b5151996c787d48a2e6 on dev/1.6.0-dev56-recovery

**Verdict** Live delivery is useful under favorable conditions. Offline recovery fails for core board and raid records, several receive paths accept unauthorized or stale state, and routine reconciliation can consume the shared send queue. Fix those before relying on KWC as the authoritative guild record in a 25–50-member guild.

This is source inspection and simulation. The audit executed the production Core, Network and guild handlers in independent Lua states with a shared simulated clock and transport. Raid attendance has an additional handler-level fixture. Actual WoW Forever server rate limits, event timing, chat restrictions, cross-realm behavior and live multi-client delivery remain unverified. Production files, SavedVariables and the installation were untouched.

## When synchronization runs

| Trigger | What happens |
|---|---|
| Login or UI reload | Core registers prefixes and attempts local HK sends. World-entry paths refresh honor, request Guild Service immediately, schedule achievement points at ~4 s, version announce and Full Sync at ~12 s, and a separate honor request at ~18 s. Initial roster event can add earlier requests. Raid Sign-Ups rides Full Sync plus its own roster trigger. |
| Guild join or switch | Roster refresh and delayed Full Sync (~8 s). Guild Service/version do not have a dedicated guild-change repair path. Saved tables and queued work lack a guild namespace. |
| Another client comes online | The new client's requests can trigger replies. Existing clients may reconcile on guild roster events, gated by a 120 s window, or by five-minute polling. No dedicated verified peer-online handshake. |
| Local change | Board/actions, RSVP, honors and supported live events usually queue immediate messages. Raid Command assignments require Publish. Attendance records require manual sharing. Notes are local. |
| Return from offline | Same login triggers, subject to relay authorization, saved cache availability, size limits, drops and stale dependencies. |
| Simultaneous reconnect | Independent requests and all-peer broadcasts. Cooldowns and jitter change timing; no single responder or per-request manifest. |
| Zone/instance transitions, including BG entry/exit | If the client fires PLAYER_ENTERING_WORLD, it reuses the login path without filtering initial-login/reload flags. Guild Service samples on zone/group events; honor also refreshes on HK/honor events, debounced CRITERIA_UPDATE and its five-minute ticker. No separate BG state event is required by the native snapshot model. |
| Logout and later return | Saved data persists through ordinary logout/reload; the in-memory queue does not. No acknowledgement or durable outbox confirms that the last update was sent. |

Opening KWC can trigger auto sync (120 s window). Manual Full Sync covers boards, tombstones, honor and sign-ups. Guild Service has its own request path; Raid Command has a group Request Sync action; Raid Tools attendance requires inventory/pull/push; roster may require confirmation; guild version discovery explicitly queries with Addon Checker. Manual Full Sync uses the same receive rules, so it cannot bypass the offline failures. The auto-sync toggle does not disable independent PvP polling, Guild Service, scouting or other subsystem timers.

| **Critical — RSVP impersonation, reproduced.** RaidSignup.lua onMessage RS (lines 113–126). A member submitted another roster member's RSVP with revision 2147483647. | The receiver checks that the claimed player exists, without authenticating a third-party relay or binding fresh updates to the sender. A forged revision can lock out legitimate responses. | Separate direct writes from cache replies and verify origin/authority. Bound revision progression. | **Critical — early succession, reproduced.** Operations.lua ApplyCommandEvent / TrySuccession (224/283) and Sync.lua applyCommandEvent (178). A named lieutenant sent P while the current commander was online. A different sender claiming the officer actor was rejected. | Local generation checks offline status; the receiver accepts any sender matching the appointed lieutenant and chain. No stable ordering for conflicting L/P/R. Bound and expire pending IDs globally, suppress seen event IDs before deferring. KWC uses WoW's delivered sender plus local roster/role checks. There is no cryptographic authentication of claimed records. Incoming KWC3/KWC4 board traffic requires the GUILD event channel, but legacy writes and several request types rely on that channel rather than checking the current roster. KWC4 snapshot writes and PVPCACHE/HKAREACACHE have more checks. They still cannot prove the original actor supplied a relayed payload. The tests do not establish that a client can fabricate the server-provided sender field.

## Traffic and test methodology

Active prefixes are KWC3 (operations, responses/claims/sightings, joins, death, honor and achievement totals, Service), KWC4 (board state, deletes and command), KWCS1 (scout), KWRS1 (sign-ups), KWCCHK (version), KWCR2 (PARTY/RAID command), and KRTools (AceComm group traffic and addon whispers, including attendance/roster, ready status and group version). KWCDEL1 is declared but unused. Board packets cap at 225 bytes; raid sign-up/command at 240; shared queue at 250. AceComm has its own serialization, compression, fragmentation and ChatThrottleLib path. Large recovery can starve unrelated sends on the shared KWC queue.

The isolated test uses actual send queues and protocol receivers. It simulates 0.1–3.0 s variable delivery, occasional drops and copies per recipient, and a transport throttle every 83rd attempted send. Delivery also respects the simulated guild and offline state. The 5–25-client cases use the committed pre-split PvP implementation on every fifth peer. Lua table traversal can vary across runtimes or runs, so traffic figures and end-state counts are observations, not exact predictions. Guild-channel byte counts include addon prefix and message bytes once per successful send, excluding server framing, recipient fan-out, dropped send attempts, actual chat and the separate AceComm transport. Load results are for a synthetic guild with 60 retained bounties, 25 tombstones and 10 sign-ups per peer. Active traffic includes any previously queued recovery, one publisher making 12 HK/sighting changes in one minute, a bounty and a new scheduled raid.

Each traffic cell gives **successful packets / bytes**, summed across the guild. Login starts simultaneously. The 210 s drain window follows login with no user changes. In the manual test all simulated clients request Full Sync together. Its window includes scheduled traffic. After the active minute the simulation runs another four minutes before reading convergence.

Raid creation in this load fixture happened after the sender's officer cache was older than 180 s, with no periodic roster refresh mocked. This tests stale-cache behavior rather than estimating live raid sign-up success. The ideal-delivery fixture with a fresh roster verified live creation. No guild size reached all measured convergence targets.

- Reloading one client in the small ideal-delivery fixture produced 52 packets / 2,606 bytes guild-wide in 40 seconds. The reloaded client retained cached HKs and an existing tombstone.
- Empty two-client idle baseline after warm-up was 60 packets / 2,238 bytes over 15 minutes, or 4 packets per minute guild-wide. The 25-client loaded post-login drain averaged 472 packets per minute without user changes.
- The large recovery fixture used 100 CTAs, 200 tombstones, 20 sign-ups with RSVPs, and 200 Guild Service observations. One requester triggered 83 successful packets / 5,480 bytes in 70 s. The responder dropped 159 enqueue attempts and still had 303 queued. This run used ideal delivery.
- Shared transport attempts roughly one send every 0.85 s per client, about 70/minute before backoff. A full 350-packet queue therefore needs about five minutes to drain under continuous successful sends. The 25-client run had 6,821 simulated recipient delivery losses, 5,807 injected duplicate copies and 136 send throttles. It ended with 50 queued packets in aggregate. The separate large recovery fixture is where enqueue overflow was demonstrated.
- In ideal delivery, the returning client missed a bounty, resolved CTA, CTA response and raid sign-up once their original author disconnected. The same client recovered the offline author's split HKs from a peer. Manual requests use the same authorization rules. In a restart fixture two days later, an ordinary peer restored cached split HKs. The edited bounty was still absent and a deleted CTA remained visible. Guild Service separately rejects samples older than 45 days by source inspection.
- The existing seven suites passed. The new audit suite reproduces known failures by design. Lua 5.1 syntax passed on 93 files, and the existing initialization suite loaded all 72 TOC entries in order.

## Final answers

1. **Does everything intended to be guild-wide synchronize automatically?** No. Several live writes are automatic, while attendance, Raid Command publishing, roster confirmation and some discovery paths need user actions. Multiple intended guild records lack working automatic recovery.
2. **Does it work without manual Sync?** Live delivery often does. Automatic requests run on common triggers. Manual Sync uses the same rules and cannot repair several demonstrated failures.
3. **Can offline players catch up from any online holder?** Sometimes for PvP totals. Ordinary peer recovery fails for unknown board entries and sign-ups, tombstones held by a non-officer, and several child records. Attendance requires a manual pull.
4. **Can duplicate or stale messages corrupt data?** Yes. Replayed status packets can reopen resolved records; same-version edits can diverge; old totals can overwrite displays; repeated sightings crowd out real ones.
5. **Are bounty/CTA deletions reliable?** No. Online known-record deletion from an authorized sender worked. Unseen deletes were discarded and a later stale creation reappeared.
6. **Do PvP counters inflate through duplicate synchronization?** Exact duplicates do not add kills. Reordered lifetime data, aliases and fabricated cache values can still produce inaccurate rankings. Native split snapshots had better replay behavior.
7. **Can leadership be spoofed?** Simple actor impersonation was rejected. An appointed lieutenant could force an early promotion; stale roster authority and inconsistent identity comparisons widen the trust gap.
8. **Is there unnecessary addon traffic?** Yes. Repeated guild-wide snapshot replies and overlapping scheduled requests produce redundant transfers and compete with live writes.
9. **Is it completely silent?** No. Core sync uses addon traffic; local chat output still includes startup, errors and legacy CTA alerts. Ready Check can attempt player-visible version whispers. Whether the target client permits each attempted whisper needs live verification.
10. **What blocks 25–50-member use?** First close the unauthorized write and disclosure paths. Then fix guild scoping, deterministic revisions, durable deletes and child-record recovery. Add bounded, targeted catch-up and prove convergence and queue headroom under loss before verifying 2–5 real Forever clients and a larger live raid.

Keep the manual Full Sync entry point for diagnostics. The readiness gate is authorized state convergence with the original writer offline, bounded traffic under reconnect and live activity, no background player-chat output, and real-client verification of transport and UI behavior.
